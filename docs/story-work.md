> 대상 작업: yuna.page(연아 소개 미니 홈페이지 + QR 명함)를 만든 과정
> 작성: 2026-10-09 · **교정: 2026-10-10 (실제 경험 반영)**

## 손작업 순서
1. (내가) 처음엔 명함에 연락처만 담을까 했지만, 명함만으로는 연아 소개가 너무 제한적이라 미니 홈페이지 + QR로 방향을 틀었다.
2. (내가) 담을 소개와, 친구 부모님에게 받을 항목(이름·전할 말·회신 수단·희망 일정)을 정했다.
3. (내가) 어느 정도 모양이 나온 뒤, 연아에게 '소개하고 싶은 것'과 '장래희망'을 직접 물어 반영했다.
4. (내가) 과한 선택지는 덜어내고(간소화), 캘리그라피(손글씨)·낙서 요소·BGM을 더해 유쾌하게 고도화했다.
5. (내가) 보여주고 싶은 게 많아 사진은 9장 두되, 첫 화면 부담을 줄이려 '더보기'로 접었다.
6. (내가) 완성된 버전에 URL을 붙이고 QR을 추출해 명함 작업으로 넘어갔다.
7. (내가) 명함은 아이들이 쓰는 걸 고려해 때가 덜 타고 덜 구겨지는 재질로 잡고, 모서리는 귀도리(둥글게)로 뾰족함을 없앴다.
8. (내가) 인쇄 전 실제로 QR을 찍어 페이지 접속을 확인하고, 요청이 오면 문자·메일로 연락하고 처리 상태를 적었다.

## 추출 — 산출물 (명사)
연락 방식 결정(명함→홈페이지) · 소개 소재(사진·그림·문구) · 연아 인터뷰(소개·장래희망) · 받을 항목 정의 · 간소화된 폼(덜어내기) · 유쾌한 톤 요소(캘리그라피·낙서·BGM) · 9장 갤러리 + 더보기 · URL · QR · 명함(재질·귀도리) · 접수된 요청 · 처리 상태 기록

## 추출 — 멈칫 (게이트 후보) — 실제 (2026-10-10)
- **G1) 소개 사진을 몇 장까지?** 보여주고 싶은 게 많아 9장, "굳이 막을 필요 있나" 싶었고 결국 **'더보기'로 접어 해결.** (게이트: 첫 화면 즉시 노출 사진 ≤ N, 나머지 더보기) 〔문장 5〕
- **G2) 요청 폼 선택지가 너무 많아 피로도↑?** → 실제로 **'덜어내기'로 대응**(간소화). 〔문장 4〕
- **G3) 개인정보 수집 '동의' 절차가 이 규모에 굳이 필요한가** 〔문장 2〕
- **G4) 알림이 문자·메일로 실제 수신되는가 / 메일이면 실시간 확인되는가 (아니면 문자 API 필요)** 〔문장 8〕
- **G5) 명함 물성 — 아이가 쓰는 명함이라 때·구김·뾰족함이 걱정** → 때 덜 타고 덜 구겨지는 재질 + **귀도리(모서리 둥글게)** 로 기준화. 〔문장 7〕

## 추출 — 넘김 (에이전트 경계) — 실제 (2026-10-10)
- **H1) 콘셉트 전환**: 명함(연락처만) → 미니 홈페이지(소개 중심) 〔문장 1→2〕
- **H2) 아빠 → 연아 (사람 바뀜)**: 담을 내용 기획 → 연아에게 소개·장래희망 직접 묻기 〔문장 2→3〕
- **H3) 콘텐츠 → 디자인 톤**: 덜어내기 + 캘리그라피·낙서·BGM 입히기 〔문장 3→4〕
- **H4) 완성 → 제작**: URL 붙이기 → QR 추출 → 명함(재질·귀도리) 작업 〔문장 6→7〕
- **H5) 웹 접수 → 실제 연락**: 웹으로 요청 받음 → 아빠가 직접 문자·메일로 연락 〔문장 8〕
