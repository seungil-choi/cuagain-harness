# harness.md — yuna.page 디자인 파이프라인

> 하네스 4요소 = **페이즈 · 산출물 · 게이트 · 에이전트.**
> 게이트는 전부 **숫자 또는 파일 존재 여부**로 판정한다(통과=숫자가 기준을 만족).
> 페이즈 경계는 `story-work.md`의 **넘김(H1~H3)**, 게이트는 **멈칫(G1~G3) + 서비스 ★1·★2**에서 왔다.

## 흐름 요약
```
P1 소재·요구 정리 → P2 화면 흐름 설계 → P3 디자인 적용 → P4 검증·판정
      (H1)              (H2)              (H3)
```

---

## P1. 소재·요구 정리
- **에이전트**: 기획 정리 역할 — PRD/스토리를 읽고 "무엇을 받고 무엇을 보여줄지" 확정.
- **산출물**: `docs/story-service.md`(유저스토리 5 + ★2), 소개 소재 목록, 요청 입력 항목 목록.
- **게이트 G1 (숫자)**:
  - 유저스토리 수 = **5** (US-1~5 존재)
  - ★(어기면 안 되는 것) 수 ≥ **2**
  - 입력 항목 중 아동 민감정보(학교·학급·생일·주소) 필드 수 = **0**  ← ★2
- 넘김 **H1**: 소재 선정 → 화면 설계.

## P2. 화면 흐름 설계
- **에이전트**: IA/흐름 역할 — 화면 목록과 순서(소개→안내→폼→완료)를 잡는다.
- **산출물**: 화면 목록(공개 소개+폼 / 접수 완료 / privacy), 각 화면의 섹션 순서.
- **게이트 G2 (숫자/존재)**:
  - 핵심 화면 정의 수 ≥ **2** (소개+폼, 접수 완료)
  - 첫 화면에서 "연아 아빠에게 보내기" 주 행동 = **1개** (주 버튼 1)
  - 공개 화면에 노출된 관리자 링크 수 = **0**
- 넘김 **H2**: 흐름 → 디자인/제작.

## P3. 디자인 적용
- **에이전트**: UI 디자인 역할 — `docs/design.md` 토큰·컴포넌트 규칙으로 실제 화면을 만든다.
- **산출물**: `runs/<run>/index.html` (소개+폼+완료 상태), design.md 토큰 적용.
- **게이트 G3 (숫자)**:
  - design.md 색 토큰 사용 수 ≥ **7**, 타이포 스케일 ≥ **6**
  - 주 버튼/터치 타깃 최소 높이 ≥ **44px** (위반 0)
  - 입력 필드 `label` 연결 수 = **필드 수** (누락 0)
  - `alt` 없는 의미 이미지 수 = **0**
- 넘김 **H3**: 제작 → 운영(요청 접수/연락)은 범위 밖(이 하네스는 **공개 화면까지**).

## P4. 검증·판정
- **에이전트**: 검수 역할 — 게이트를 센다. 하나라도 기준 미달이면 해당 페이즈로 되돌린다.
- **산출물**: `runs/<run>/gate-report.md` (게이트별 실측 숫자 + 통과/실패).
- **게이트 G4 (숫자)**:
  - 360px 가로 스크롤 = **0**
  - 색만으로 상태 전달하는 지점 = **0**
  - 공개 화면에 타인의 요청/연락처 노출 = **0**  ← ★1
  - US-1~5 중 화면 요소로 커버된 수 = **5/5**

---

## 왜 이렇게 나눴나 (5가지 팁 반영)
1. **두 도메인에서 출발** — 서비스(PRD→story-service) + 작업(내 경험→story-work).
2. **작업 흐름으로 게이트 위치** — 멈칫 G1/G2/G3가 실제 페이즈 경계가 됨.
3. **PRD로 판정 기준** — ★1·★2가 P1·P4 게이트의 합격선.
4. **지시 말고 라운드로 질문** — 각 페이즈 진입 시 질문→기본값→승인(CLAUDE.md).
5. **게이트는 셀 수 있게** — 전부 숫자/파일 존재로 판정(위 G1~G4).
